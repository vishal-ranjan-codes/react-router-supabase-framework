# Tooling decisions

Why the repo is wired the way it is. Read this before "simplifying" something here — most
of these choices have a failure mode behind them.

## Lint and format: Biome, not ESLint + Prettier

`@biomejs/biome` 2.6.3 is the single tool for linting, formatting and import sorting.

The trade-off that decided it: ESLint with `typescript-eslint` typed rules plus Prettier
plus `eslint-plugin-react-hooks`, `jsx-a11y`, `import`, `tailwindcss` needs ~6 packages and
a config that has to be re-validated every time one of them releases a major. Biome covers
the same ground in one binary, is an order of magnitude faster (it checks this repo's 138
files in well under a second), and its TypeScript/JSX/TSX/CSS/JSON support is built in.
For a starter that every new project inherits, the config that has to be maintained is the
cost that actually compounds.

What was given up, and how it is handled:

- **No type-aware rules.** Biome lints syntax, not types. `tsc -b` (via `npm run typecheck`)
  is the type gate, and it is strict, so the classic "unsafe any / implicit any" holes stay
  closed.
- **No `react-hooks/exhaustive-deps` parity.** Biome's `useExhaustiveDependencies` covers
  the common cases. It flagged one genuine finding here — `app/hooks/use-toast.ts`
  re-subscribed its listener on every state change; that effect now has `[]` deps.

Scripts:

| Script                            | Runs                                        | Use                                                           |
| --------------------------------- | ------------------------------------------- | ------------------------------------------------------------- |
| `npm run lint` / `lint:fix`       | `biome lint .` (`--write`)                  | rules only                                                    |
| `npm run format` / `format:check` | `biome format --write .` / `biome format .` | layout only                                                   |
| `npm run check` / `check:fix`     | `biome check .` (`--write`)                 | lint + format + import sorting; this is what CI runs stepwise |

## What Biome deliberately does not touch

`biome.json` excludes:

- `app/components/ui/**` from the **linter** only — these are vendored shadcn files. Their
  `React.forwardRef`-free but dense patterns (`asChild`, `cva`, `any`-typed props) generate
  hundreds of findings we will never fix upstream, and silencing them inline would be noise.
  They are still **formatted**, so the folder looks like the rest of the repo.
- `app/types/database.types.ts` — generated by `supabase gen types`, so any manual fix is
  overwritten on the next regeneration.
- `app/globals.css` — the design-system token blocks (`@theme`, `@custom-variant`) are
  hand-aligned; re-wrapping them makes review diffs unreadable.
- `package-lock.json`, `pnpm-lock.yaml`, `supabase-email-templates/` (hand-written HTML with
  Liquid-style `{{ .ConfirmationURL }}` placeholders that Biome would re-indent).

Generated-but-gitignored files (`worker-configuration.d.ts` from `wrangler types`,
`.react-router/`, `build/`, `coverage/`, `.wrangler/`) never reach Biome in the first place:
`vcs.useIgnoreFile: true` means anything in `.gitignore` is skipped automatically, so those
do not need listing twice.

## Line endings

`.gitattributes` sets `* text=auto eol=lf`. Without it, a Windows clone with the common
`core.autocrlf=true` checks the tree out as CRLF, Biome writes LF, and every `npm run
format` shows a whole-repo diff. Commit `i/lf` + working `w/crlf` was the pre-existing state
for ten files; they are normalised now.

## Dual package manager support

The repo is a starter, so projects fork it with either npm or pnpm. Both work, and both are
verified in CI. Supporting them "without conflict" required four explicit decisions:

1. **No `packageManager` field in `package.json`.** Adding one makes Corepack force that
   package manager on everyone, which is exactly the wrong thing for a template that must
   stay neutral. `.nvmrc` pins Node instead, which both package managers honour.
2. **Both lockfiles are committed** (`package-lock.json`, `pnpm-lock.yaml`) and CI installs
   with `npm ci` / `pnpm install --frozen-lockfile`, so drift fails the build instead of
   surfacing as "works on my machine".
3. **Install-script policy is expressed twice, once per tool.** Only two dependencies in
   the whole tree run install hooks (`esbuild`, `workerd`), and both are required at
   runtime — `workerd` _is_ the dev/deploy execution environment:
   - npm reads `allowScripts` in `package.json` (npm normalises the entries to exact
     `name@version` pins; refresh it when those packages change major).
   - pnpm 10+ silently skips unapproved build scripts, so `pnpm-workspace.yaml` lists the
     same two under `onlyBuiltDependencies`.
4. **Tooling detects the caller.** `playwright.config.ts` starts the dev server with
   `npm run dev` or `pnpm dev` based on `npm_config_user_agent`, so `pnpm test:e2e` does not
   end up driving the server through the other package manager.

Regenerating the pnpm lock without disturbing an npm-installed `node_modules`:

```bash
npx --yes pnpm@latest install --lockfile-only
```

`pnpm-workspace.yaml` exists only to carry `onlyBuiltDependencies`; the project is not a
workspace, and that is also why the file is empty apart from that key.

## CI

`.github/workflows/test.yml`:

- Triggers on `master` **and** `main`. The original workflow only listed `main`, which does
  not exist in this repo, so CI had never run.
- `quality` job runs an `npm` / `pnpm` matrix: install, lint, format check, typecheck, unit
  tests, build. Fail-fast is off so one package manager's failure does not hide the other's.
- `e2e` job installs only chromium and passes `--with-deps`; `playwright.config.ts` narrows
  `projects` to chromium when `CI` is set, so the two agree. Locally all three engines run.
- Node comes from `.nvmrc` (`node-version-file`), so CI, local and `engines.node` cannot
  drift apart.

## Unwired dependencies and known gaps

Honest list, so nobody mistakes "unused" for "dead":

- **`zod`** is a dependency but `app/` does not import it yet. Validation today is
  hand-rolled at the edges that need it (`app/lib/r2/keys.ts`, the route-level form checks in
  `app/routes/sign-in.tsx` and friends). Add zod where the first real domain form appears —
  and take the v4 major before writing against v3's error API.
- **R2 goes through `@aws-sdk/client-s3`**, which contributes the ~867 kB server chunk in
  `npm run build`. Cloudflare's native `r2_buckets` binding would remove that dependency and
  the S3 credentials from `.dev.vars`; it costs portability (the code stops working outside
  workers). Left as-is because the S3 path also works against any S3-compatible store.
- **Rate limiting is per isolate.** `app/middleware/rate-limit.ts` keeps its window table in
  module scope, so a scaled-out Worker enforces the limit per isolate, not globally. A
  correct global limit needs KV/Durable Objects. Documented in the file's own comment.
- **`.dev.vars` is required for local work** and is gitignored. `npm run dev` starts workerd,
  and workerd reads secrets from that file — a missing `.dev.vars` degrades the app to "auth
  not configured" (503 from the sign-in action) rather than crashing, which is intended.
- **Webhook signature format** is `x-webhook-signature: t=<unix-seconds>,v1=<hex>`; see
  `app/lib/webhooks.ts` and the README for `wrangler secret put WEBHOOK_SECRET`.
